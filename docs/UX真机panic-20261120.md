# 真机 panic：UX 模块 pick 路径 NULL 解引用（2026-11-20）

**结论：本地编出的 `sailboat_sched_assist.ko` 在 `-UXmodBase-` 底座上加载、启用、打标签后触发内核 panic。禁止刷机，禁止把该 ko 交付使用。**

## 现场

- 底座：`5.15.225-Sailboat-ColorOS-UXmodBase-20261120`（ABK run `44683587474`，`CONFIG_OPLUS_SCHED_ASSIST=m`，无内建 SA）。
- 加载方式：`fastboot boot` 一次性试启动（未写分区）→ `insmod /data/local/tmp/sailboat_sched_assist.ko`，`insmod_rc=0`。
- 初始化正常：`sailboat_coloros_ux_min: ready, runtime disabled`，`init_state=1 init_errno=0 init_stage=5`，`lsmod` 显示 `[permanent]`。
- 打开总开关 `echo 1 > sched_assist_enabled` → `active=1`。
- 打标签 `echo "p <pid> 1" > ux_task` 后计数器开始动：`set=1`、`enqueue=85`、`selected=84`、`runtime=20`，随后涨到 `enqueue=337 selected=329 runtime=93`。
- panic 发生在 `uptime=285.36s`，即模块 active 约 190 秒、正在做 UI 滚动负载时。

## 定位

用同一底座的 `System.map` + `vmlinux` 反汇编，`pick_next_task_fair+0x1b4` 就是：

```asm
1a3c3c: bl     update_curr
1a3c44: mov    x1, x23              ; curr
1a3c48: bl     pick_next_entity
1a3c4c: ldr    x21, [x0, #344]      ; ← se->my_q，即 group_cfs_rq(se)
```

`x0 = 0`，`offset 344` 对应 `struct sched_entity` 的 `my_q`。所以 **`pick_next_entity()` 返回了 NULL**，`group_cfs_rq(NULL)` 踩空。

内核源码侧该调用位于 `pick_next_task_fair()` 的 `again:` 内层：

```c
	do {
		struct sched_entity *curr = cfs_rq->curr;
		if (curr) { ... update_curr(cfs_rq); ... }
		se = pick_next_entity(cfs_rq, curr);
		cfs_rq = group_cfs_rq(se);      /* se 为 NULL 即 panic */
	} while (cfs_rq);
```

入口守卫是 `if (!sched_fair_runnable(rq)) goto idle;`，而

```c
static inline bool sched_fair_runnable(struct rq *rq)
{
	return rq->cfs.nr_running > 0;
}
```

`pick_next_entity()` 的两条选择路径都可能返回 NULL：`sched_feat(EEVDF)` 走 `abk_pick_eevdf()`，其收尾是

```c
	if (!best)
		best = curr && curr->on_rq ? curr : __pick_first_entity(cfs_rq);
	return best;
```

`__pick_first_entity()` 在 `cfs_rq->tasks_timeline` 为空时返回 NULL。`CONFIG_FAIR_GROUP_SCHED` 下 `rq->cfs.nr_running > 0` 只说明层级里有可运行实体，**不保证顶层 `tasks_timeline` 非空**（任务全在子 cgroup 时顶层就是空的）。此时 `curr` 又不在 rq 上，`abk_pick_eevdf` 返回 NULL，上游没有二次保护，直接踩空。

**这是 ABK EEVDF 回移树上潜在的可达缺陷；我们的模块让它在本机被走到。**

## 归因

控制实验：同一 `newboot.img`、**不 insmod 我们的模块**、跑同样的唤醒+滚动+三个应用反复启动负载，`dmesg` 无 `Oops/BUG/panic`，设备未重启。加载模块并启用 UX 后同样量级负载即 panic。

因此 panic 由本模块引发，**不是底座自带问题**（至少不是在该负载下自发出现）。

我们注册的 hook 里唯一落在该路径上的是 `android_rvh_replace_next_task_fair`（`sailboat_coloros_ux_pick`）。它把 `*task`/`*entity` 改成我们自己 `orq->ux_list` 里的候选，随后的上游代码会

```c
	if (prev != p) {
		struct sched_entity *pse = &prev->se;
		while (!(cfs_rq = is_same_group(se, pse))) {
			...
			set_next_entity(cfs_rq_of(se), se);   /* fair.c:8220 */
			se = parent_entity(se);
		}
		put_prev_entity(cfs_rq, pse);
		set_next_entity(cfs_rq, se);
	}
```

`set_next_entity()` 会 `__dequeue_entity()` 把实体从该层 `tasks_timeline` 摘掉并写 `cfs_rq->curr`。候选来自另一棵红黑树、且不限制与 `prev` 同 cgroup 时，这条链会在多个层级上被改写，而 `abk_pick_eevdf()` 的收尾 `__pick_first_entity()` 对空树没有保护、入口又只查了根 `nr_running`，于是下一次挑选拿到 NULL。

**这是目前最可能的作用点，但尚未最终锁定**：需要带符号的 minidump（`/data/vendor/diag/minidump.gz`，78 MB）或在模块内加断言重跑才能定案。本节不下确定性结论。

## 已排除的两种猜测

- `android_rvh_replace_next_task_fair_handler` 里 `simple && repick` 的 workaround 用 `for_each_sched_entity()` 自底向上调 `set_next_entity()`，看着和上游 `simple:` 路径的自顶向下方向相反。复核后**不是 bug**：实体固定时两者覆盖同一批 `(cfs_rq, se)` 对，且 `put_prev_task()` 已对 `prev` 做了对称的全链 walk。
- `enqueue_ux_thread()` 有 `global_sched_assist_enabled` 门禁而 `dequeue_ux_thread()` 没有。复核后**不是缺陷**：`get_task_struct`/`put_task_struct` 与 `orq->nr_running` 在四种启用状态组合下都配平；反过来给 dequeue 加门禁才会破坏"启用中入队、禁用后出队"的配平。

## 已实施的加固与真机复验结果

`sailboat_coloros_ux_pick()` 增加约束：只允许候选与调度 hook 显式传入、即正在被换下的任务（`prev`）处在**同一个 `cfs_rq`**。不能用 `rq->curr` 代替 hook 参数推断 outgoing task；测试覆盖 `rq->curr != prev`。空 `prev`、非 fair `prev` 或空 outgoing `cfs_rq` 均不选候选。此时上游的 walk 退化为空操作，`set_next_entity()` 只作用在单层，不会引入跨 cgroup 的树改写。

第一版把该约束并进了"过期"判定，结果跨 cgroup 候选被 `update_ux_timeline_task_removal()` 从 UX 链表里摘掉——它只是暂时选不中，不该移除（`rejected` 一度冲到 230 而 `enqueue` 不动）。已改成独立分支：约束不满足走 SKIP 路径，留在链表里继续找下一个。

真机复验（内核已用系统内 `dd` 持久化刷入 `boot_a`，见下）：

```text

enqueue=3660   dequeue=3660
```

模块 active 约 230 秒（上次 panic 在 190 秒）持续 UI 滚动 + 三个应用反复启动，`dmesg` 无 `Internal error` / `Kernel panic` / `kernel BUG at` / `Call trace`，设备未重启。pick 路径被真实走到（2153 次选中、1345 次运行）。

代价：约 77% 的候选因 cgroup 不符被跳过（`hierarchy_skipped` 7178 vs `selected` 2153）。这是当前为稳定付的成本，记录在案，后续按"先证明稳定、再逐步放宽"处理。

**仍未最终定位根因**：约束绕过了触发条件，但没有证明 `abk_pick_eevdf()` 返回 NULL 的确切来源。要定案仍需 `/data/vendor/diag/minidump.gz` 或模块内加断言重跑。

## 刷入与复现（系统内 dd，不再走 bootloader）

内核已持久化刷入，模块未开机自加载。复现/复验：

```powershell
adb -s <serial> shell "su -c 'sh /data/local/tmp/ux_sustained.sh'"
```

`out/ux_local_tools/ux_sustained.sh` 会唤醒屏幕、给 surfaceflinger 和 launcher 打标签，然后持续 300 秒滚动 + 定时切应用，每 30 秒采样一次计数器。模块是常驻的（`[permanent]`），换版本必须重启一次。

若需重新刷内核或回滚：

```powershell
adb push out/ux_local_44683587474.1eYtZ0/kernel/newboot.img /data/local/tmp/newboot.img
adb shell "su -c 'dd if=/data/local/tmp/newboot.img of=/dev/block/by-name/boot_a bs=1M conv=fsync'"
adb shell "su -c 'sh /data/local/tmp/rollback_boot.sh'"
```

刷入与回滚都要校验：刷入后 `su -c "dd if=/dev/block/by-name/boot_a bs=1M count=64 | md5sum"` 应与本地同样范围 `dd if=newboot.img bs=1M count=64 | md5sum`（或 `head -c 67108864 newboot.img | md5sum`）一致，不要拿 64 MiB 的摘要去比整个镜像；回滚前先确认 `su -c "md5sum /dev/block/by-name/boot_a"` 与 `boot_a.backup.img` 一致，否则不要写。

`ux_task` 的写入格式是 `p <pid> <ux_value>` 三个 token（`OPT_STR_TYPE` 必须是 `p`），两个 token 会返回 `-EINVAL`。

**负载要真**：屏幕黑着或前台页面不可滚动时 surfaceflinger 不出帧，`enqueue`/`selected` 完全不动，会误判成模块没工作。先确认 `dumpsys power | grep mWakefulness` 为 `Awake`，并在可滚动页面上划。
